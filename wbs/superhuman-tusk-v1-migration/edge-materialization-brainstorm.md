# superhuman-wbs edge materialization — brainstorm

Triggered by the post-tusk#406 reframing in the S2 brainstorm: the pack declares its four edges (`wbs-parent`, `wbs-about`, `wbs-supersedes`, `wbs-blocks`) as **standalone edge types** with no ref-property pair, so no markdown content carries edge instances. The DB-only persistence + deterministic-reindex contract that Tusk gives us is intact; we're just not using it. Question: should we convert to ref properties so the workspace is reproducible from markdown, or accept the imperative `tusk edge add` ceremony as part of the pack's UX?

This brainstorm is a sibling to the S1.5 polish pass — same pack, similar small-delta nature. Outcome will either become a new Story (S1.6, before S2 implementation), be deferred to a later Story, or be a recorded "stay with status quo" decision.

## How Tusk's ref-property → edge synthesis works

From `~/projects/tusk/internal/manifest/loader.go:257-282` (`buildEdgeTypeFromRef`):

| Aspect | `type = "ref"` (singular) | `type = "list-of"`, `item-type = "ref"` |
|---|---|---|
| Cardinality | `many-to-one` (fixed) | `many-to-many` (fixed) |
| Ordered | always `false` | `false` by default; `true` if property declares `ordered = true` — uses `OrderedBy = "order"` (the auto-assigned ordinal) |
| Acyclic | carried verbatim from `prop.acyclic` | carried verbatim from `prop.acyclic` |
| Inverse | carried verbatim from `prop.inverse` | carried verbatim from `prop.inverse` |
| `from` | the owning node type (singular) | the owning node type (singular) |
| `to` | `prop.to` | `prop.to` |
| `OrderedBy` (custom property) | not available | not available — always `"order"` when ordered |

A pack cannot declare both `[edge-types.X]` and a ref property named `X` — `loader.go:325` errors with: *"edge type X is auto-generated by ref property … remove the explicit [edge-types.X] declaration or rename the property"*. They are mutually exclusive.

## Per-edge conversion analysis

### wbs-about — clean conversion

Current standalone:

```toml
[edge-types.wbs-about]
from = ["wbs-note"]; to = ["wbs-node"]; cardinality = "many-to-one"
ordered = false; acyclic = true; inverse = "wbs-notes"
```

As ref property on `wbs-note`:

```toml
{ name = "wbs-about", type = "ref", to = "wbs-node", acyclic = true, inverse = "wbs-notes" }
```

All four constraints carried. Edge instances now expressed in `wbs-note` frontmatter: `wbs-about: wbs/superhuman-tusk-v1-migration`. ✓ Clean.

### wbs-supersedes — clean conversion

Current:

```toml
[edge-types.wbs-supersedes]
from = ["wbs-note"]; to = ["wbs-note"]; cardinality = "many-to-one"
ordered = false; acyclic = true; inverse = "wbs-superseded-by"
```

As ref property on `wbs-note`:

```toml
{ name = "wbs-supersedes", type = "ref", to = "wbs-note", acyclic = true, inverse = "wbs-superseded-by" }
```

All constraints carried. ✓ Clean.

### wbs-blocks — clean conversion (with shape change)

Current:

```toml
[edge-types.wbs-blocks]
from = ["wbs-node"]; to = ["wbs-node"]; cardinality = "many-to-many"
ordered = false; acyclic = true; inverse = "wbs-blocked-by"
```

As list-of-ref property on `wbs-node`:

```toml
{ name = "wbs-blocks", type = "list-of", item-type = "ref", to = "wbs-node",
  acyclic = true, inverse = "wbs-blocked-by" }
```

All constraints carried. Edge instances expressed in frontmatter as a list. ✓ Clean.

### wbs-parent — real trade-off

Current:

```toml
[edge-types.wbs-parent]
from = ["wbs-node"]; to = ["wbs-node"]; cardinality = "many-to-one"
ordered = true; acyclic = true; inverse = "wbs-children"
```

Two conversion attempts, neither preserves everything:

**Attempt 1 — singular ref on the child:**

```toml
{ name = "wbs-parent", type = "ref", to = "wbs-node", acyclic = true, inverse = "wbs-children" }
```

- ✓ many-to-one (correct — each child has one parent)
- ✓ acyclic
- ✓ inverse "wbs-children"
- ✗ **`ordered = true` is silently dropped.** The synthesizer ignores `ordered` on singular refs. We lose the auto-assigned ordinal that the S1.5 brainstorm pinned as the priority signal.

**Attempt 2 — list-of-ref on the parent:**

```toml
{ name = "wbs-children", type = "list-of", item-type = "ref", to = "wbs-node",
  ordered = true, acyclic = true, inverse = "wbs-parent" }
```

- ✗ **many-to-many** instead of many-to-one (the synthesizer fixes cardinality for list-of-ref). A child could technically have multiple parents. Tree shape isn't enforced.
- ✓ ordered (list order preserved)
- ✓ acyclic
- ✓ inverse "wbs-parent"

Neither attempt is strictly equivalent. The S1.5 decision — "priority signal rides on `wbs-parent` ordinality, no separate property" — depends on edge-ordinality at the engine level, which neither ref-property shape gives us for a true many-to-one relationship.

## Options

### A. Status quo: standalone edges, DB-only, imperative adds

- All four edges stay as today's `[edge-types.X]` declarations. No ref properties.
- Workspaces re-run `tusk edge add` after every fresh checkout / DB rebuild.
- The orphan-wbs-nodes warning in S2 surfaces the situation; users follow the documented remedy.
- **Pro:** zero schema churn; S1.5's design intact; full edge constraints preserved (`cardinality = many-to-one`, `ordered = true` per parent).
- **Con:** workspace state isn't reproducible from markdown / git. Real ceremony every fresh checkout. The migration project loses 8 edges every time the DB rebuilds — recreating them is a script.

### B. Convert all four to ref properties, accept losses on wbs-parent

- wbs-about, wbs-supersedes, wbs-blocks convert cleanly (option B.1 below).
- wbs-parent: pick Attempt 1 (singular ref, lose ordering) and reverse S1.5 — add an explicit `priority` enum/int back to wbs-node, or drop priority signaling entirely.
- **Pro:** workspace reproducible from markdown. No ceremony. Aligned with Tusk's local-first contract.
- **Con:** reverses an S1.5 design decision. Adds either `priority` property (S1.5 explicitly rejected) or accepts "no priority signal at all." Loses many-to-one strictness on the alternative parent-side shape.

### C. Hybrid: convert the three clean cases, keep wbs-parent standalone

- wbs-about, wbs-supersedes, wbs-blocks → ref properties.
- wbs-parent → keeps `[edge-types.wbs-parent]`. Still imperative on fresh checkout, but the other three edges (specs/plans/brainstorms attached to nodes, supersession chains, dependency edges) become reproducible from markdown.
- **Pro:** partial alignment with local-first contract. Preserves S1.5 ordinality-priority decision.
- **Con:** mixed model — pack docs and skills need to explain why three edges work one way and one works another. The most-frequently-added edge (wbs-parent, one per node) is still the imperative one, so most of the "edges-vanish-on-rebuild" pain remains.

### D. Defer pending Tusk's customizable-ordinals feature

- Tusk has the customizable-ordinals follow-up planned (per the #406 resolution).
- That feature may unlock: a ref-property variant that supports per-(parent, edge-type) ordinal control, or a way for standalone edges to be sourced from markdown via a different mechanism.
- Until that lands, keep status quo (Option A). Revisit when the upstream feature is concrete.
- **Pro:** no premature design churn. Defers a decision that the upstream may obsolete.
- **Con:** indefinite timeline. The fresh-checkout pain persists.

## Recommendation — superseded by Tusk v1.3.0 (2026-05-19)

The four-option framing above is **obsolete**. Tusk v1.3.0 shipped three relevant features simultaneously:

- **[#400](https://github.com/germanamz/tusk/pull/400)** — explicit `--ordinal` flag on `tusk edge add`. Custom ordinal control is now a first-class CLI primitive (the customizable-ordinals feature that gated option D).
- **[#407](https://github.com/germanamz/tusk/pull/407)** — traversal shortcuts respect a per-edge `hierarchy` alias on EdgeType. Closes [#405](https://github.com/germanamz/tusk/issues/405). Packs can now declare `hierarchy = "<alias>"` on their parent-shaped edge and use `tree:<alias>=<id>` in queries.
- **[#409](https://github.com/germanamz/tusk/pull/409)** — `tusk edge add` and `tusk edge remove` (and their MCP equivalents) now **write the edge into the source node's frontmatter**, then reindex the source file. From the new help text: *"The change is durable: the edge lives in git-tracked markdown, not in the index database. Running `rm .tusk/index.db && tusk reindex` recovers the same graph state."*

Net effect: standalone `[edge-types.X]` declarations no longer have the local-first gap. The previous reasoning that "non-ref edges live only in the DB" no longer holds — every `tusk edge add` is a markdown mutation. Options A, B, C, D are all retired by upstream.

### What this pack needs to do to land on v1.3.0

The v1.3.0 changes also tightened `ordered` validation: `ordered = true` is now an alias for `ordered = "order"` and the `from` node type **must** declare a sortable `order` property. Our pack fails this validation today:

```
$ tusk edge add --type wbs-parent --source <a> --target <b>
manifest: edge-types.wbs-parent: ordered = "order" references property "order" which is not declared on node-type "wbs-node"
```

Concrete pack changes for v1.3.0 compatibility:

1. **Add `order: int` to `wbs-node` properties** (matching kanban's fix in #409 / built-in `kanban.toml`).
2. **Declare `hierarchy = "wbs"` on `[edge-types.wbs-parent]`** so the `tree:wbs=<id>` qualified shortcut works in queries (the per-edge alias from #407).
3. **Bump the pack's documentation comments** to mention v1.3.0 as the minimum Tusk version (the `order` property requirement and the frontmatter-writing edge-add behavior).

Existing edges in workspaces that were added under v1.2.0 are still DB-only (they predate #409's frontmatter writes). One-time remediation per workspace: remove and re-add each edge via the v1.3.0 CLI / MCP — the re-add will write to frontmatter and survive future reindexes.

### Updated implications for S2

The orphan-wbs-nodes warning surfaces an honest state: the markdown frontmatter doesn't declare the parent. The fix is `tusk edge add` (which now writes frontmatter). The "this is a known pack-design gap" qualifier in the previous brainstorm version is no longer accurate — the pack-design gap was real but is now resolved at the primitive level by Tusk.

S1.5's priority-via-ordinality decision is **preserved** — `--ordinal N` on `tusk edge add` gives explicit control, and `ordered = true` still produces the auto-assigned-ordinal-per-parent behavior our skill design relies on. No reversal needed.

### Next moves

This brainstorm itself is now a record of a deferred-and-then-resolved-by-upstream decision. The actual work is:

1. Small pack update (`order: int` property + `hierarchy = "wbs"` alias + doc comments) — sized like S1.5; could be S1.6 or rolled into another small PR.
2. Re-materialize the existing edges in this workspace so they live in markdown going forward (one-time per workspace; the rest of this branch's S2 work needs the edges to be reachable).
3. Update the S2 brainstorm's orphan-warning framing — done in a separate edit.
